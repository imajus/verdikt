# Roadmap — ERC-8004 Validation Registry interop

**Status: post-hackathon research.** Not scoped for the ETHOnline 2026
submission — there is no bonus track for it, and the standard itself is still
`Draft`. This document records what ERC-8004 is, why it lines up with what
Verdikt already produces, and the one place the two models disagree — so the
integration is a deliberate design decision later rather than a rediscovery.

## What ERC-8004 is

ERC-8004 ("Trustless Agents") adds a trust layer on top of agent-communication
protocols (Google's A2A, Anthropic's MCP), which route messages between agents
but assume the agents already trust each other. It defines **three registries**,
deployable on any EVM chain:

- **Identity Registry** — each agent is an ERC-721 token (`agentId` = the
  `tokenId`) pointing at an off-chain registration file (an A2A-`AgentCard`-
  compatible document) via `agentURI`. The file carries a `supportedTrust` array
  such as `["reputation", "crypto-economic", "tee-attestation"]`.
- **Reputation Registry** — client-authorised, **subjective** feedback
  (`giveFeedback(...)`), an on-chain audit trail of who said what about an agent.
- **Validation Registry** — **objective** proof of work: an independent validator
  records a verifiable outcome for a specific piece of the agent's work.

The split matters for us: Verdikt's per-call `PASS`/`FAIL`/`DOWN` is objective
proof of delivery, so it belongs to the **Validation Registry**, not the
Reputation Registry.

Status caveats, to be stated plainly wherever we cite this:

- The EIP text at `eips.ethereum.org/EIPS/eip-8004` is **`Draft`**. Press and
  blogs calling it "finalised" mean *reference contracts were deployed to
  mainnet* (~Jan–Feb 2026), not that the EIP reached `Final`. The interface can
  still move; the reference implementation's v1.0 is already **not** backward-
  compatible with its v0.4. **Do not build production on it until it settles.**
- Authors: Marco De Rossi, Davide Crapis, Jordan Ellis, Erik Reppel. Created
  2025-08-13. Requires EIP-155/712/721/1271.

## The Validation Registry interface

From the ERC-8004 reference implementation (`ChaosChain/trustless-agents-erc-ri`,
`src/ValidationRegistry.sol`), matching the EIP text:

```solidity
function validationRequest(
    address validatorAddress,   // who is allowed to answer
    uint256 agentId,            // the agent whose work is validated
    string calldata requestURI, // off-chain pointer to the work/evidence
    bytes32 requestHash         // KECCAK-256 commitment to that content; the primary key
) external;                     // MUST be called by the agent's owner or operator

function validationResponse(
    bytes32 requestHash,        // ties the answer to the request
    uint8   response,           // 0-100 (0 = fail … 100 = pass, or a score in between)
    string  calldata responseURI,  // off-chain evidence/detail
    bytes32 responseHash,       // commitment to responseURI
    string  calldata tag        // free-form bucket, e.g. an SLA category
) external;                     // MUST be called by the validatorAddress named in the request

function getSummary(
    uint256 agentId,
    address[] calldata validatorAddresses,
    string calldata tag
) external view returns (uint64 count, uint8 averageResponse);
```

Events `ValidationRequest` and `ValidationResponse` carry `validatorAddress`,
`agentId` and `requestHash` as indexed topics; an indexer pairs request to
response on `requestHash` and buckets by `tag`. Reference-impl hardening beyond
the spec: `requestHash` is globally unique and cannot be overwritten, and
self-validation (validator == agent owner) reverts.

The standard is unopinionated about *how* a validator reaches its answer. It
names two families and stores only the outcome, leaving incentives/slashing to a
"specific validation protocol" layered on top:

1. **Crypto-economic / re-execution** — a staked validator re-runs the work.
2. **Cryptographic attestation** — zkML validity proofs, or **TEE attestation**
   (work run in an enclave whose measurement is posted). This is the
   `"tee-attestation"` trust tag.

## Why Verdikt already fits — and where it doesn't

Verdikt's confidential CRE workflow (Specification §2) *is* the second kind of
validator: an attested TEE that judges an agent's paid response and emits a
verdict. Verdikt produces, today, exactly the object the Validation Registry
exists to record. The mapping is mostly direct:

| ERC-8004 field | Verdikt source |
| --- | --- |
| `validatorAddress` | Verdikt's CRE DON / `workflowOwner` — the attested TEE. Registers with the `"tee-attestation"` trust model. |
| `agentId` | A Verdikt service. Today its identity is `serviceId = keccak256(slug)` on Arc plus the `<slug>.verdikt.eth` subname (§3, §4); interop means the service *also* mints an ERC-8004 Identity NFT. |
| `response` (0-100) | Verdikt's aggregate `conformance`/`availability`, already **0–1000 integers** (§1), rescaled to 0–100. |
| `tag` | The two ratios map cleanly to two tags, `"conformance"` and `"availability"` — `getSummary(agentId, [verdiktValidator], tag)` then returns each independently. This is the natural home for Verdikt's deliberate two-score split (§1). |
| `requestHash` / `responseURI` | A commitment, **not** the response body. Verdikt's invariant is that the observed value never touches a chain (§CLAUDE, "Invariants"); `requestHash` can commit to redacted evidence and `responseURI` point at an enclave measurement, preserving confidentiality. |

**What Verdikt gains.** Its verdicts and reputation live today in the
`verdikt.eth` namespace and on Arc — readable, but Verdikt-specific. Publishing
to the Validation Registry makes Verdikt-verified reputation legible to *any*
ERC-8004-aware agent or marketplace, and positions Verdikt's TEE validator as a
first-class validator in the trustless-agents ecosystem. That is the interop
story: Verdikt as an ERC-8004 **validator**, not just a private proxy.

### The sharp mismatch: who initiates validation

ERC-8004's handshake assumes the **agent requests validation of its own work**
(`validationRequest` MUST come from the agent's owner/operator; the named
validator then answers). Verdikt inverts this: the agent (provider) neither
chooses nor invokes the validator — Verdikt validates unilaterally on every paid
call, whether the provider wants it or not, which is the whole point of
proof-of-service. Two reconciliations, to be decided later:

- **Standing authorisation.** At registration the provider issues a standing
  `validationRequest` naming Verdikt's validator, so Verdikt is pre-authorised to
  post responses. Clean, but stretches the per-call `requestHash`-keyed model
  toward a per-service subscription.
- **Wait for a validator-initiated path.** A v2 of the spec may support
  validator-pushed records; the request/response asymmetry is an open design
  question in the standard already.

### Which path publishes, and to which chain

- **Publish from the hourly aggregate, not the per-call path.** Verdikt keeps the
  confidential per-call path to a single `VerdictWritten` write (§3); adding a
  third-registry write per call costs gas and latency inside the enclave for no
  gain. The hourly reputation workflow (§1, §2) already computes the 7-day
  ratios and writes them to ENS — mirroring that same write to the Validation
  Registry as two tagged summaries is the low-cost, correct seam, and matches
  ERC-8004's `getSummary` shape.
- **Cross-chain.** ERC-8004 registries deploy on mainnet/L2s (Base, etc.);
  Verdikt's verdicts live on **Arc**. Options: deploy the registry on Arc, or
  bridge via **CCIP** — Chainlink already positions CRE + CCIP for exactly this
  in the ERC-8004 ecosystem, so it composes with our stack rather than adding a
  new dependency.

## Open questions in the standard (inherited if we integrate)

- **Validator honesty is out of scope of ERC-8004** — the registry records
  outcomes but guarantees nothing about validator integrity; slashing/incentives
  are external. Verdikt's answer is TEE attestation, which is a strength to lead
  with here.
- **On-chain vs event-only data**, reputation-aggregation danger (a single score
  is "dangerous" because trust is contextual/directional), sybil resistance, and
  Validation-Registry storage exhaustion are live debates on the EIP thread.
- **Privacy** — the *existence* and metadata of every validation are public even
  when the payload is a commitment. Compatible with Verdikt's "observed value
  never on-chain" rule, but worth restating for sensitive providers.

## Ecosystem note

x402 and ERC-8004 are positioned as complementary (identity/reputation/
validation + the payment rail). The closest published analogue to Verdikt's use
case is **Cortensor's** three-phase x402 + ERC-8004 plan, which carries an
`sla_tier` in its access pass and publishes to the Validation Registry by
default — worth reading directly before we commit to a design. Chainlink CRE/CCIP
and TEE-based validation (Oasis) already appear in the ecosystem, so Verdikt's
stack is a native fit rather than an outsider.

**"vet402" is unverified.** It was raised as a project that "uses the ERC-8004
Validation Registry," but no authoritative source or repo could be found. If it
resurfaces as a comparable, get a URL before treating any of its claims as real.
